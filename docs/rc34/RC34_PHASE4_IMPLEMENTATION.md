## 1. 実装概要・画面構成

ホームのRC別取り込みパネルを「ルアーマスター管理」ボタン1つに置き換えた。管理画面から以下へ移動する。

| 画面 | 内容 |
| --- | --- |
| マスター管理 | アプリ同梱版、購入指定オプション、統一差分確認・CSV・バックアップ・最終確認・適用結果 |
| 開発履歴 | RC33〜RC19の15件。カタログ追加のないRCを含む概要・主要機能・保留事項・関連資料 |
| 取り込み履歴 | IndexedDBの実履歴、復元イベント、実行日時・実件数・結果・エラー・データ文脈 |
| 旧形式データの取り込み | RC7/RC18カタログJSONの従来互換処理 |

管理画面はアプリ内のscreenとして切り替え、URLルーティングや外部サービスは追加していない。対象版の表示は `lureMasterManifest.masterVersion` を用いる。「最新版」はアプリに同梱された版と明記し、サーバーの最新版確認・適用済み宣言を行わない。

## 2. 既存RC別UIの整理

ホームからRC19/20/21/22/28/30/31/33の個別更新ボタンを撤去した。新しい管理画面・開発履歴・取り込み履歴にもRC別実行ボタンは設けていない。

旧 `src/LureCatalogImportPanel.vue` とRC別apply・データ・実装資料のソースは削除せず保持した。旧パネルはAppから使用しない。新しい更新操作は、RC別applyを順番に呼ぶ処理には接続していない。

旧JSONの処理だけを `LegacyLureCatalogPanel.vue` に切り出し、詳細入口へ移した。元の `previewLureCatalog / importLureCatalog` をそのまま使用し、入力IDの対応付け、カテゴリ更新の範囲、所有情報の無視、エラー・衝突表示、適用前confirmを維持した。バックアップ復元は従来のホーム入口に残し、3操作を画面上でも区別した。

## 3. プレビュー・最終確認・共通apply

差分確認はPhase 1の `previewLureMaster({ includePurchases })`、適用はPhase 3の `applyLureMaster(comparisonToken, { includePurchases })` を直接使用する。DB v10／バックアップv9や、Phase 1〜3のエンジン・照合処理は変更していない。

プレビューでは、対象版、6種類の追加予定、既存カラー・代表配色・所有の保持数、保留色数、画像／名称推定／未確認の分類を表示する。保留があっても不足する確認済み対象だけを適用できる。保留色と別配列の要確認注記は区別する。

モデル一覧は5件単位でページングする。各モデルに追加・保持・保留を集約し、詳細ではカラー・理由・元RC・出典を表示する。カラーはモデルごとに先頭20件まで表示し、全件はCSVで確認する。1,084色を一度に画面へ列挙しない。

CSVは表示中の計画から作成し、plannerを再実行しない。`kind=plan` と対象版、メーカー、シリーズ、モデル、コード、カラー、追加／保持／保留、理由、元RC、出典URL、既存ID、所有／配色予定を保存する。BOM、引用符・改行、表計算の数式開始文字を処理し、実績CSVとは表示しない。

購入指定は「RC33の購入指定もマイルアーへ登録する」、初期OFF。11個の対象名を折りたたみで確認できる。オプション変更時は計画・バックアップ保存確認・最終確認を破棄して再プレビューする。異なるオプションで古いトークンを流用しない。

### 更新手順

1. 差分確認のみではDBを書き換えない。
2. 「更新前のバックアップを保存」で既存 `exportBackup()` を実行する。失敗時は最終確認へ進まず、applyも呼ばない。
3. ダウンロード開始を保存完了とみなさず、利用者に「ファイル」等で保存実体を確認してもらう。
4. 最終確認に対象版・追加予定・保留・所有オプションを再表示する。保存確認チェックがない限り実行ボタンは無効。
5. 「確認して更新を実行」で初めて共通applyを開始する。取消やホームへ戻る操作では更新・開始履歴の書き込みを行わない。
6. 結果にはapplyが返した `counts / history` の実追加・保持・保留と実行日時・状態を表示する。予定値は実績に転用しない。

二重操作は画面のbusyとハンドラーのガードで抑止し、データ整合性はPhase 3の再照合・トランザクションに依存する。`STALE_PREVIEW` は再プレビューを要求する。更新失敗・履歴保存失敗には成功画面を表示せず、保存状態・空き容量・現在の差分を再確認する案内を出す。

追加0件でも保留が残れば「保留あり成功」と表示する。保留のない追加0件だけが「変更なし」となる。完了後は結果見出しにフォーカスし、実績を見失わず取り込み履歴へ進める。

## 4. 開発履歴・取り込み履歴

開発履歴は静的な日本語テキストをJSへ同梱し、RC番号の降順で15件表示する。各RCのカタログ対象・主要機能・保留事項・実装資料を折りたたみ表示する。カタログ追加がないRC23〜27・29・32も含む。開発履歴を端末の適用実績として扱わない。

GitHubの資料リンクは補助情報で、概要の閲覧には通信不要。未承認座標候補のJSON等は同梱・参照せず、RC25は調査の概要と正式実装側の資料を表示する。既存docs・Git履歴は保持した。15件を折りたためるため、この段階で検索・フィルターは追加していない。

取り込み履歴は新ストアを読み取り専用で取得し、sequenceの降順・5件単位でページングする。状態ラベルは成功／保留あり成功／変更なし／失敗／中断と、runningに対する「確認不能（実行中または中断未確認）」。開始・完了時刻は端末ローカル時刻で表示する。

履歴には6対象の実追加・保持・保留、所有オプション、対象マスター版、エラー、保留理由・出典を表示する。理由は初期10件、明示操作で10件ずつ展開する。SHA-256・照合規則版・データ文脈は詳細表示に置き、復元イベントは元バックアップ版・出力時刻・文脈切替を別表示する。

履歴がなければ「この端末には取り込み履歴がありません」と表示する。旧適用日時を推定しない。削除・再適用ボタンはなく、再読み込みはDBの読み取りだけを行う。過去の成功から現在のマスター状態を判定せず、管理画面で毎回差分確認を行うよう案内した。

## 5. PWA・iPhoneサイズの配慮

AppのSW安全判定へ管理画面のbusy・プレビュー状態を接続した。プレビュー中、バックアップ出力／保存確認中、最終確認中、共通apply中、旧JSONプレビュー中は切替不可。処理終了・取消後に安全な更新操作を再度有効にする。

既存の明示SW更新・他タブ拒否・自動切替なしの方針は維持する。更新コード、累積データ、開発履歴は静的バンドルに含み、既存precacheで配信する。新しい画像取得・API・runtimeCachingは追加していない。

主要ボタン・チェックラベル・展開操作は44px以上を基本にし、モデル・履歴のページング、折りたたみ、折返し、結果へのフォーカス、処理中表示を実装した。新規offline試験は402×874のタッチ条件も使用した。これは画面サイズのシミュレーションで、iPhone 17／Safari実機確認ではない。

## 6. 実証結果とデータ保護

テストは専用origin・隔離プロファイル・合成バックアップ・fake-indexeddbのみを使用した。実ユーザーバックアップや実iPhoneのIndexedDBは操作していない。

| シナリオ | 確認内容 |
| --- | --- |
| ホームと管理画面 | ホームの入口1件、RC別更新ボタンなし、同梱版の意味を表示 |
| 開発履歴 | 全RC19〜33を展開可能。個別適用ボタンなし。圏外で閲覧 |
| 取消・バックアップ保存確認 | プレビュー・CSV・バックアップ出力・取消まで全ストア不変。保存確認なしでは適用不可 |
| 購入オプション変更 | 再プレビューし、以前の最終確認・保存チェックを無効化 |
| 初回・再実行 | 実ストア増分と保存履歴の追加件数が一致。再実行は6対象とも追加0件 |
| 所有OFF／ON | OFFでは所有完全不変。ONでは不足する購入11個だけ追加。元の状態を保持 |
| エラー | バックアップ失敗ではapply開始なし。古いトークン・本体失敗・履歴保存失敗では成功表示なし、既存データ不変 |
| 履歴 | 実行時刻・対象版・件数・文脈が保存レコードと一致。runningを確認不能として表示 |
| 復元 | 成功履歴と復元イベントを残し、現在データの不足をプレビューで再検出 |
| 旧JSON | 元の事前検証・所有情報の無視・確認付き適用・カテゴリ更新規約を維持 |
| 別タブ | RC22・RC28の合成基準から、統一確認の二窓競合は1回だけコミット |
| オフライン | 冷間起動→統一プレビュー→バックアップ→適用→完全終了→再起動→履歴・開発履歴→再適用→v9出力 |
| SW競合 | 待機SWがある状態でプレビュー・保存確認・適用中のボタン無効を確認。処理中はcontroller不変、完了後に明示切替可能 |

新UIの空に近い合成カタログでは、700色・代表配色41件を追加し、元の所有3件を保持した。メーカー等の前提条件が異なるため、Phase 3の全メーカーを備えた合成DBの1,073色とは件数が異なる。UIはどちらもplanner／applyの実結果を表示し、固定の件数を埋め込まない。

RC固有の回帰は、RC20/21/22/28/30/31/33の入力を統一入口へ移行したうえで、各パックの全確認済みモデル・カラー・JAN、既存IDと全内容、未確認SSSの非作成、再実行、CSV、選択UI、v9往復を検証する共通ハーネスへまとめた。旧単体テストの照合・保留・ロールバック検証は変更していない。RC19の釣果保存、RC33の辞書逆引き・SVG、RC30のイベント編集も維持している。

### 試験中に修正した点

- 生成時に旧JSON画面と一部移行テストへ混入した日本語の文字化けをUTF-8で修正した。
- 同名の合成釣行が複数あるため、既存IDをdata属性で識別して編集対象を選ぶようにした。
- カタログの色数確認で「最近使用」の同名候補を重複集計していたため、カタログ側の候補だけを数え、50件ページング後の全件も確認するよう修正した。
- 既存RC32ブラウザ移行試験の旧期待値v9／21ストアを、現行v10／22ストアへ更新した。旧19ストアの全レコード保持と履歴の空初期値の検証は残した。
- 履歴のない端末のv8出力は空履歴ストアを省略する従来互換のため、offline側のv8出力比較も空履歴を明示検証して分離した。
- 未承認座標調査へのruntime参照を禁止する既存試験に従い、開発履歴の補助資料リンクを正式実装側の資料へ整理した。座標候補データを同梱する変更はしていない。

初回の移行後E2E全体は146件成功・4件失敗（色数集計と旧DB期待値）だった。上記を修正後、全150件が成功した。安全性検証を削除・緩和して通す対応は行っていない。
