# RC34 ルアーマスター更新機構統合：調査・設計

調査日: 2026-11-01（Asia/Tokyo）  
作業ブランチ: `feature/rc34-unified-lure-master-update`  
調査基点: `25cfb63`（RC33マージ済み）  
段階: 設計のみ。アプリコード、DB定義、配布データ、既存ドキュメントを変更しない。

## 1. 結論

統合は可能。既存の「読み取り専用プレビュー → 適用時の再照合 → 単一Dexieトランザクションによる不足分追加」を共通化する。RCごとの適用関数を順に呼ぶ方式は採用しない。照合・作成許可・保留条件が異なり、RC33には所有・配色への追加もあり、プレビューの合算と実結果が一致しないためである。

推奨構成は、アプリに同梱する累積マニフェスト、共通の差分計画・適用処理、実行履歴ストア、および独立した履歴画面。ホームの更新入口は「最新版マスターとの差分を確認」に一本化する。RC19〜RC33の資料・出典・開発履歴を残し、履歴画面から閲覧できるようにする。RC別の更新ボタンは残さない。

「最新版」は**端末で利用中のアプリに同梱された最新版**を意味する。圏外で未配信のデータを取得することはできない。アプリ更新とIndexedDBへのマスター適用を分け、どちらも既存の明示操作・更新延期の方針を維持する。

## 4. 現在のDBと互換性

### 4.1 保存・参照

- DexieのDB定義はv9、21ストア。4つのルアーマスターは数値自動採番。メーカー名のみ `&name` の一意索引があり、シリーズ・モデル・色の自然キーにはDBの一意制約がない。
- `lureSeries.manufacturerId → lureManufacturers.id`、`lureModels.seriesId → lureSeries.id`、`lureVariants.modelId → lureModels.id`。`myLures.variantId`、`catches.lureId/lureVariantId`も既存IDを参照する。
- `catalogEvidence` はvariant内の任意情報。RC22/28/30/31/33のrevision、名称、コード、JAN、出典階層、URL、重量・全長・浮力等を持つ。既存行を保持する処理では最新revisionに書き換わらない。revisionは「その端末でRCを適用した証拠」ではない。
- `lureVisualProfiles` はUUIDと `&variantId`・`&naturalKey` を持つ。`temporaryLureColors` は独立した仮配色。既存の配色自然キーはメーカー・シリーズ・モデル・コード／名称を含む。
- `catches.visualColorSnapshot` は保存時の値コピー。現在の辞書更新に合わせて再生成しない。
- `appMetadata` は現状、施設マスター用の型・検証・復元に組み込まれている。型を無視してルアー履歴を混在させない。

### 4.2 バックアップ

現行 `backup.ts` はv1〜v8を受け付け、配色辞書または配色snapshotがある場合にv8を出力する。DBのバージョンとバックアップのバージョンは別物である。

復元は、全ルアーマスターを含む対象ストアを置き換える既存の明示操作。マスター差分更新とは異なる。v1〜v7復元では、端末に残る配色の内容・自然キーを保持し、variant/modelのローカル参照を解除する。RC33は参照解除済みプロフィールとの衝突を保留し、再リンクや二重作成をしない。この規約を維持する。

古いバックアップを明示復元すれば、マスター件数もそのバックアップ時点に戻り得る。RC34更新が全件置換や自動復元を行うことはない。復元後の差分確認で不足を判定し、履歴に「適用済み」があってもスキップしない。

### 4.3 資料件数の扱い

ローカルの `docs/rc32/fishing-log-backup-2026-10-31.json` はv7で、読み取り集計はメーカー81・シリーズ155・モデル362・色2,899・所有9・釣行3・釣果15・イベント1。RC31指示書の80/152/355/2,816は別時点であり、現在の期待値に流用しない。

[RC33既存監査](../rc33/RC33_AUDIT.json) はこの資料に対して60色・所有11個・配色41件を追加し、再適用0件、既存行不変、v8往復一致を記録している。これは既存RC33の記録で、RC34の実行結果でも現在のiPhone件数でもない。実装段階では端末状態ごとの実差分を表示する。

## 5. 提案する統合方式

### 5.1 累積データと作成許可

`src/data/lureMasterManifest.ts` 等に `masterVersion`、内容ハッシュ、照合規則版、元RC、別名、親階層、商品属性、モデル作成許可、色候補・保留理由・出典を集約する。既存RCデータは削除せず、ビルド時または静的なアダプターで累積データへ変換する。閲覧用の開発履歴データは更新処理と独立させる。

RC19/20/21等の重なる商品・色を事前に対応付ける。後のRCが明示的に拡張した商品許可だけを採用し、元の出典・表記を追跡可能に残す。単純な「後勝ち」や候補数の加算は禁止。限定区分の違い・別モデルの同じコード・未確認SSSを併合しない。マニフェスト内の矛盾はビルド時検証で止める。

RC7/18の全マスターを最新パックに複製して置き換える設計にはしない。RC19以前の登録やユーザー追加データは残し、今回の確認済み累積対象に不足するものだけを補う。基礎メーカーが存在しない場合の許可も明記し、全製品に対して無条件の階層作成を認めない。

### 5.2 同一性判定

メーカーは名称・明示別名で一意に照合し、ID62/71等は資料の参考値に留める。シリーズはメーカー内、モデルはシリーズ内の正式名・別名で照合し、重量・全長・タイプ・別シリーズの同名候補も検査する。F/SS/SSSや重量の違いを削除するような一律正規化はしない。複数候補・属性矛盾はモデル単位で保留する。

色はモデル内の明示コードを優先し、コードのない既存行は正式名称・元名称・明示別名で照合する。ただしRC22/28/30の限定区分・名称・JANの整合性検査を継承する。同一モデルでも区分により同番号が再利用される場合があるため、コードだけの一律併合をしない。JAN単独で別名色を同一視しない。コードと名前が矛盾する候補を名称fallbackで迂回しない。

正規化は比較時だけ行い、保存済みの名前・コード・evidenceを変更しない。`All/Ghost`等の一般語をコード扱いしない既存規約を維持する。配色の既存自然キーはRC34用の照合キーに置き換えない。色照合のゼロ埋め吸収と配色自然キーの規約には差があるため、配色ID・自然キー・variantIdの三者を現行バリデータで再確認する。

### 5.3 共通プレビューと原子的適用

共通plannerは単一の読み取りスナップショットから、親→子の順に仮想状態を作り、複数RCの重複も含めて一つの計画を返す。確認のためにDBへ仮登録しない。

プレビューには対象版、メーカー／シリーズ／モデル／色ごとの追加・保持・保留件数、既存ID、出典、保留理由、配色・所有への影響を表示する。差分CSVも提供する。既存行の更新・削除予定は通常更新では0件とする。保留が残る場合は「確認済み対象のみ適用」と明示し、適用後も「保留あり」を残す。

適用トークンはデータ内容ハッシュ・照合規則版・選択オプション・関係ストアの安定順スナップショットを含む。適用時の単一 `rw` トランザクションで同じplannerを再実行し、一致しなければ書き込みを始めず再確認を求める。実DB採番で親IDを解決し、不足分だけ `add` する。トランザクション内で通信・ダウンロード・ダイアログ待機をしない。

同じストアを含むトランザクションで複数タブの適用を直列化する。二重クリック抑止は補助であり、UIフラグだけに冪等性を依存させない。2回目は履歴の版だけで判断せず、現データを再照合して追加0件を確認する。

### 5.4 RC33・RC32を維持する副作用の境界

通常の「マスター更新」は既存の所有・釣行・釣果・仮配色に書き込まない。RC33の61色、商品情報、出典、公式画像29件・名称推定12件の候補を累積データに含める。未登録の代表配色だけを追加予定として表示し、既存プロフィールは推定済みを含めすべて保持する。不明20件に捏造配色を作らない。

RC33の購入11個は個人情報に相当する指定であり、全利用者向けマスターに自動的な所有追加を含めることは避ける。**提案は統一プレビュー内の「購入指定の所有も登録する」オプション（初期OFF）**。対象11個と追加／既存保持を事前表示し、選択時だけ同一トランザクションに含める。RC別更新ボタンを再設置せず、RC33の購入登録能力と既存の登録結果を維持する。既存所有は非アクティブ・未確認を含め追加も状態変更もしない。

このオプション化は現行RC33ボタンの既定動作からの変更提案である。今回の設計段階では適用しない。RC32の辞書・逆引き・手動編集・名称推定入口は維持し、全マスターへの名称推定は別の明示操作のままとする。

## 6. 開発履歴と実際の取り込み履歴

### 6.1 別画面の閲覧

ホームから「マスター更新・開発履歴」画面へ遷移し、次の二つを分けて表示する。履歴画面にRC別適用ボタンは置かない。

| 種別 | 内容 | 保存先 |
| --- | --- | --- |
| 開発履歴 | RC19〜RC33の変更概要・対象データ・根拠・保留事項。マスター更新のないRCも表示 | アプリ同梱の静的データ。既存docsとGit履歴も保持 |
| 取り込み履歴 | この端末で実行した日時・対象版・実追加数・保持／保留・成功／失敗／変更なし等 | IndexedDBの専用ストア |

リポジトリのMarkdownは現在のPWAに自動同梱されない。履歴の概要・主要な仕様・出典はビルドに含め、圏外で全RCを閲覧できるようにする。詳細資料へのリンクは補助とし、外部リンクの接続を閲覧成立の条件にしない。開発日・公開日を端末への適用日として表示しない。

### 6.2 ストア案

DB v10に `lureMasterImportHistory` を追加する案を推奨する。既存21ストアや索引を変更せず、upgrade時のシード・全件補完を行わない。

| 項目 | 意味 |
| --- | --- |
| `id` | 操作UUID。`masterVersion`は一意キーにしない（同版の再実行も履歴化） |
| `kind` | `import / restore`。復元イベントは取り込み実績と分け、版・追加数等はimport時のみ必須とする |
| `masterVersion / manifestHash / matchingVersion` | 実際に使用したデータと照合規則 |
| `startedAt / completedAt` | 実行端末でのUTC ISO日時。完了前はcompletedAt未設定 |
| `status` | `running / succeeded / succeeded_with_holds / no_changes / failed / interrupted` |
| `counts` | 表別の実追加数、保持数、保留数。配色・任意所有も分ける |
| `options` | 所有登録の選択等。プレビューと同じ内容 |
| `details / errorCode` | 保留理由・対象の自然キー・結果概要。釣行メモ等は含めない |
| `contextId` | 適用時のデータ文脈。復元前後の履歴を現在状態の証拠にしないために使用 |

日時は保存時に取得し、表示は端末ローカル時刻（日本利用時はJST）とする。オフラインの端末時計なので、正確なサーバー時刻とは扱わない。過去の取り込み日時・件数は既存DBから復元できないため、RC34導入前は「実行履歴なし／日時不明」と表示する。バックアップのexportedAtやGitの日時で捏造しない。

### 6.3 成功・失敗・中断

実行開始時に短い別トランザクションでrunningを保存する。続く本体トランザクションで差分再照合・追加を行い、**実追加数と成功結果の履歴確定を同じコミットに含める**。履歴確定に失敗すればマスター追加も戻す。

本体失敗時はロールバック後の別トランザクションでfailed・実追加0件を記録する。プレビュー予定数を実追加数として保存しない。プレビュー後の競合も失敗理由として識別する。履歴自体が保存できない容量不足等では成功表示せず、履歴保存失敗を画面で明示する。

クラッシュや強制終了でrunningが残った場合、他タブで処理中でないことを確認できたものだけinterruptedとする。経過秒数だけで実行中タブを中断扱いしない。成功コミット済みなら履歴も成功になっているため、完了を推測しない。確認・取消だけでは取り込み履歴を作らない。追加0件でも明示的な「再照合結果を保存」を用意しno_changesを残せるようにする。

## 7. バックアップ互換の設計案

履歴も保存・移行できるよう、履歴を持つ出力にバックアップv9を導入する。現行のv8専用分岐（配色検証等）をv9でも通るように拡張し、旧v1〜v8入力を引き続き受け付ける。履歴がない場合の従来の形式選択は維持する。旧アプリはv9を読めないため、旧版アプリへの新形式の復元は互換対象外と明記する。

v9は履歴のUUID、日時、状態、非負の件数、版・内容ハッシュ、重複を復元前に検証する。履歴に既存variantIdを必須参照として保存せず、自然キー・表示名と集計を中心にする。

復元は既存の本体データ置換・施設マージ・旧配色参照解除を維持する。端末の取り込み履歴は消さず、v9の履歴をUUIDでマージする。同一UUID・同内容は保持、同一UUID・異内容は復元全体を拒否する。旧v1〜v8復元は端末履歴を保持する。復元に伴う新しいcontextIdを別の復元イベントとして記録し、過去の「成功」を復元後の現在マスター状態と混同しない。履歴マージ・復元イベントも既存復元トランザクションに含める。

旧バックアップ復元後の不足は次の共通プレビューで表示し、自動再適用しない。配色参照解除済みとの衝突は現行RC33同様に保留する。

## 8. データ保護・PWA・主なリスク

| リスク | 方針・検証ポイント |
| --- | --- |
| 固定ID・名称正規化の差 | RC21/22の固定ID条件を共通処理へ持ち込まない。任意採番fixture、別名・複数候補・型／重量差で確認 |
| RC間重複・限定色の同番号 | 累積マニフェストの事前検証と仮想状態で重複を防止。色・モデルの原表記と区分を保持 |
| 分割適用による途中状態 | RC別関数を連続実行せず、単一計画・単一コミット。途中例外・履歴保存失敗を注入 |
| 所有の意図しない増加 | 通常更新でmyLuresを書かない。購入オプション選択時のみ不足分追加。RC23の釣果保存経路は呼ばない |
| 配色・履歴snapshot破損 | 既存代表配色・仮配色・釣果snapshotは更新しない。旧復元後の参照解除を維持 |
| 適用済み版の過信 | 版や履歴でスキップしない。毎回現データと照合し、復元・手動追加後も差分判定 |
| SW更新・別タブ競合 | `busy/preview`公開とAppの安全判定を継承。プレビュー・取り込み中はSW切替を延期。DBのversionchange/blocked表示も維持 |
| 圏外で必要データが欠落 | 全対象・保留・配色値・開発履歴をJS等に同梱。現行precache対象はhtml/js/cssで、追加JSON/mdは自動対象にならない点に注意 |
| Safariの容量・強制終了 | IndexedDBへ保存。容量不足は失敗扱い、既存行を残す。事前バックアップ出力は本体transaction前。ダウンロード開始を保存実体確認とは扱わない |
| 大きいプレビュー・ファイル | 安定順のトークン・モデル単位の表示集約で負荷を抑える。コード分割時は必要チャンクのprecacheを確認。IndexedDB transaction中の非DB非同期待機を避ける |

既存の `runtimeCaching: []`、明示SW更新、`skipWaiting: false`、`clientsClaim: false` を維持する。圏外適用時にメーカー画像やAPIを取得しない。出典URLは証跡として保存し、配色値は同梱データを使う。初回オンラインで圏外準備を完了した後、圏外起動→確認→適用→完全終了→再起動→履歴確認まで成立させる。

## 9. 実装手順案と受入条件

1. RC間の対応表・作成許可・区分・保留条件を確定し、累積マニフェストと共通plannerを実装する。既存RCの出典データと回帰期待値を保持する。
2. DB v10の履歴ストアとバックアップv9を追加する。データ文脈は同ストアの復元イベントで管理する。旧DBからの追加的upgrade、v1〜v8復元、v9往復と履歴マージを先に検証する。
3. 共通applyで再照合・採番・追加・履歴成功確定を一体化する。購入オプションと配色の保護を接続する。
4. 更新入口を一本化し、差分・結果・履歴画面を実装する。旧RC別UIを外し、開発履歴・旧JSON互換入口を別画面へ移す。旧データ・docsを削除しない。
5. 既存・新規の回帰試験、製品ビルド、offline試験、Safari/PWA実機確認を行う。実装結果を設計時の予定と区別して報告する。

| 受入対象 | 必須の確認 |
| --- | --- |
| 初回・再実行 | RC19相当、RC21相当、RC31相当、RC33適用済み、任意採番・一部不足の合成DBで2回適用。2回目は4表・配色・任意所有すべて追加0件。元からある重複を消さず、新規重複0件 |
| プレビュー | 確認・取消で全ストア不変。件数はRC間で重複計上せず、保留理由・実ID・出典を表示。古いトークン・オプション変更・別タブ変更は適用拒否 |
| 保全 | 既存21ストアの全既存行をID・内容まで比較。通常更新で所有9件等を勝手に増やさない。手動配色・仮配色・snapshot・気象・タックル・施設等も不変 |
| RC33 | 61色候補と出典、画像29・名称12・不明20の分類、購入11指定を維持。購入OFF／ONと、既存非アクティブ・未確認所有の保持を検証 |
| 原子性・履歴 | 途中書き込み失敗・成功履歴保存失敗で本体全体がrollback。失敗0件、成功の実件数、変更なし、中断復旧を再起動後も確認 |
| 復元 | 旧v1〜v8受入、旧形式の配色参照解除、v9往復、履歴のUUIDマージ・競合拒否。復元後も履歴に頼らず不足を再検出 |
| 履歴画面 | RC19〜RC33を圏外で閲覧。RCごとの更新ボタンなし。開発日と実行日時を区別 |
| PWA | 製品ビルドを固定して既存offline試験＋統一更新・履歴再起動・SW更新延期を検証。iPhoneサイズのChromiumとSafari実機を区別して報告 |

実装時の基本コマンドは `npm.cmd test`、`npm.cmd run build`、`npm.cmd run test:e2e:typecheck`、`npx.cmd playwright test`、ビルド固定後の `npx.cmd playwright test -c playwright.offline.config.ts`。現行のRC別ボタンを操作するE2Eは統一入口へ移し、RC固有データ・安全性の期待値は残す。

## 10. 今回の成果と未検証事項
