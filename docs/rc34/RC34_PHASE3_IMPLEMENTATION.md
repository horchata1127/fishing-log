実施日: 2026-11-01（Asia/Tokyo）  
ブランチ: `feature/rc34-unified-lure-master-update`  
基点: `ad206de`（Phase 2）。開始時に `e74ad5b` → `ad206de` の履歴とブランチを確認。追跡ファイルの変更なし、既存の未追跡資料等は保持。  
関連: [設計](RC34_DESIGN.md)、[Phase 1](RC34_PHASE1_IMPLEMENTATION.md)、[Phase 2](RC34_PHASE2_IMPLEMENTATION.md)

## 1. 実装概要

`applyLureMaster(comparisonToken, options?)` を追加し、累積マニフェスト・共通plannerと履歴保存APIを接続した。既存UIからはまだ呼び出さない。起動時処理・自動インポート・実端末適用は追加していない。

主なAPIは以下。

| API | 用途 |
| --- | --- |
| `applyLureMaster(token, options?)` | 既存DB・累積マニフェストに対する明示的な差分適用 |
| `hashLureMasterManifest(manifest?)` | 正規化したマニフェストJSONのSHA-256 |
| `recoverInterruptedLureMasterImports()` | Web Lockによる排他を取得できた場合だけ、中断した同プロトコルの履歴を確定 |
| `createLureMasterUpdater(database?, manifest?)` | 同じ実装を独立したDB接続や検証用マニフェストで使用。`preview / apply / recoverInterrupted` を返す |

返却値は `{ plan, counts, history }`。`plan`は再照合・保留を含む計画、`counts`と`history.counts`は確定した実績。追加数は各DB書き込みが成功してから増やし、コミット済みの場合のみ成功結果として返す。予定件数を実績としてコピーしない。

## 2. 再照合・採番・原子性

適用手順は次のとおり。

1. 対象マニフェスト・所有オプションを固定し、SHA-256を計算する。WebCrypto待機はIndexedDBトランザクションの外で行う。
2. Web Locks対応時は更新用の同一origin・同一DB名の排他ロックを取得し、証明可能な中断だけを復旧する。
3. Phase 2のAPIでrunning履歴を別トランザクションに保存する。
4. マスター4表・myLures・lureVisualProfiles・履歴を含む単一rwトランザクションで現在のDBを再読込し、`planLureMaster()`を実行する。
5. 比較トークンが異なれば、データの書き込み前に `STALE_PREVIEW` で拒否し、再プレビューを要求する。
6. 不足分だけをメーカー→シリーズ→モデル→カラーの順に `add` し、仮IDを実採番IDに対応付ける。必要な所有・代表配色を追加し、実績と成功履歴を同じトランザクションで確定する。
7. 本体が失敗した場合は全体をロールバックし、別トランザクションで実追加0件のfailed履歴を保存する。

仮IDの対応にはテーブル種別も持たせ、別ストアの同じ数値IDへ誤接続しない。正の親IDも実在を確認する。最終的なカラー→モデル→シリーズ→メーカーの参照と、代表配色の自然キー・参照も検証する。共通applyを既存トランザクション内から呼び、開始履歴と本体を意図せず一体化する呼出しは拒否する。

既存マスター・所有・配色へのupdate/deleteは使わない。書き換えるのは今回開始した履歴の状態だけである。仮配色、釣行、釣果、配色snapshot、イベント、タックル、魚種、施設、気象は更新対象に含めない。

## 3. Phase 1・2への変更理由

### Phase 1

- プレビューの6ストア読込を `readLureMasterSnapshot()` として共有し、プレビューと実適用が同じ入力をplannerへ渡すようにした。読み取り専用プレビューの規約は変えていない。
- 新規のRC19/20/21相当カラーにも `catalogEvidence` を計画するよう補完した。Phase 1は旧RCの規約に合わせてこの証跡を省略していたが、共通applyで追加する新規データにも出典・コード・区分等を永続化するために必要だった。対応するrevisionの型も追加した。
- モデル・色の照合、正規化、別名、商品作成許可、限定区分、JAN検査、保留条件は変更していない。既存カラーへの証跡の後付けや上書きもしない。累積マニフェストの内容は変更していない。

### Phase 2

- 履歴APIに省略可能なDB接続引数を追加した。別接続の本体トランザクションに、その同じ接続の履歴確定を参加させるため。
- 履歴の任意フィールド `executionProtocol: 'rc34-web-lock-v1'` を追加した。Web Lockを使った実行と旧処理を識別し、他のrunning履歴を誤って中断にしないため。
- DB v10・22ストア、バックアップv9の版は維持。新ストア・索引・upgrade書き込みは追加していない。旧履歴でexecutionProtocolが未設定でも受け入れる。

Phase 1・2の実装報告書は変更していない。

## 5. 所有・配色・既存RC33の保護

`includePurchases` は初期OFF。OFF時は既存所有が完全不変。ON時だけRC33購入指定11個の不足を追加する。既存の同色所有が非アクティブ・未確認・placeholderでも、追加や状態昇格を行わない。

公式画像29件・名称推定12件を新規代表配色として登録し、不明20件には配色を作らない。出典・画像URL・名称推定器版・根拠・確信度も保存する。既存の手動・写真・名称推定プロフィールはすべて保持する。釣果の値コピーと仮配色も不変だった。

自然キーやvariantIdの競合・参照解除済みプロフィールはplannerで保留する。新規UUIDはカタログ書き込み前に割り当て、既存UUIDまたは他の新規候補との衝突があれば影響するモデルを保留する。そのモデル専用の追加操作を除外し、他の有効な対象が使う親操作だけを残す。UUID衝突を強制した検証で、既存辞書のUUID・内容が不変であることを確認した。

既存 `applyRc33Catalog` を隔離DBへ適用した状態では、61色・所有11個・配色41件をそのまま保持し、共通applyは残る1,012色だけを追加した。所有と配色の追加は0件だった。元のID・証跡・配色状態もすべて保持した。

## 6. 履歴と失敗時の挙動

履歴に、実際の開始・完了日時、マスター版、SHA-256、照合規則版、所有オプション、データ文脈、6ストアの追加・保持・保留件数、保留理由と出典、エラーを保存する。SHA-256はキー順を安定化したマニフェスト全体のJSONから計算し、テストでNodeの独立したSHA-256実装とも一致した。

保持数は対象候補に一致した既存レコードのユニーク件数で、対象外の個人データを合算しない。既存所有が同じ色で複数あれば個体単位で数える。失敗時の実追加数は全ストア0件であり、再照合済みの保持・保留結果は残す。

成功履歴の確定失敗は本体もロールバックする。その後のfailed履歴さえ保存できなければ `HISTORY_WRITE_FAILED` を返し、runIdと元エラー・履歴エラーを識別可能にする。成功結果は返さず、開始時のrunning履歴が残る。開始履歴の保存が失敗した場合は、本体への書き込みを始めない。

## 7. 別タブ・中断・復元

データ整合性は、関係ストアを含むIDBトランザクションと、その内部の比較トークン再照合で確保する。UI側のフラグやWeb Locksだけに依存しない。

同じDBへ接続した2つの独立Dexie接続から、同じプレビューで所有ONのapplyを並行実行した。Web Locksあり／なしの双方で、一方だけが成功し、他方は`STALE_PREVIEW`となった。カラー・所有・配色の重複や部分適用はなく、履歴は成功1件・失敗1件だった。

中断復旧は、同じDB名のWeb Lockを排他取得できた場合に、そのプロトコルを使用したrunningだけを`interrupted`にする。実行中の別タブがロックを保持していれば、明示的な中断確認は何も変更しない。Web Locks非対応時、またはプロトコル未設定の旧履歴については、自動で中断認定しない。端末時計の経過時間は判断根拠にしない。

復元後は新しいデータ文脈で現在のDBを照合する。実適用後に元の合成v8バックアップを復元し、過去の成功履歴が残った状態から再適用して1,073色の不足を検出・追加、その次は追加0件を確認した。履歴を含むv9バックアップの検証も成功した。
