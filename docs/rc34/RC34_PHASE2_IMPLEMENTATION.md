## 履歴の保存仕様

DB v10は `id, contextId, sequence, startedAt, kind, status` の索引を持つ新ストアだけを追加する。既存DBのupgrade直後は空で、過去の実行日時や成功履歴を推測して補完しない。

| 項目 | 保存内容 |
| --- | --- |
| `id / kind` | 操作UUID、`import` または `restore` |
| `contextId / sequence` | データ文脈UUIDとイベント順序番号 |
| `startedAt / completedAt` | 実行端末で取得するUTC ISO日時。実行中はcompletedAtを持たない |
| `status` | `running / succeeded / succeeded_with_holds / no_changes / failed / interrupted` |
| importの版情報 | `masterVersion / manifestHash / matchingVersion`。ハッシュはSHA-256形式の64桁小文字16進文字列 |
| importの件数 | マスター4表・所有・代表配色について、それぞれ `added / retained / held` |
| `options / details / error` | 所有登録オプション、自然キーと理由、エラーコード・メッセージ |
| restoreの情報 | 元バックアップ版・出力日時、可能な場合は復元前の文脈UUID |

`startLureMasterImport(identity)` は新規のrunning履歴を保存し、`finishLureMasterImport(expected, outcome)` が完了する。完了時には保存済みrunningレコードとの全内容一致を確認し、二重確定や古い要求を拒否する。成功・変更なしの確定時にデータ文脈が変わっていた場合も拒否する。

成功は実追加あり・保留なし、保留あり成功は保留件数あり、変更なしは追加・保留とも0件として区別する。実行中・失敗・中断の実追加数は0件に制限し、失敗・中断にはエラー情報を必須とする。件数、UUID、UTC日時、日時の前後、版、ハッシュ、オプション、未知フィールド等を検証する。

APIは履歴の件数を保存する機能であり、まだ実マスターへの適用件数を収集する共通applyではない。次Phaseのapplyで実際の書き込みと成功確定を同じ親トランザクションに含められることをテストした。履歴保存エラーは呼出元へ返し、完了したことにはしない。

中断は明示的な結果として保存できる。経過時間や再起動だけでrunningを中断に変換する処理はない。別タブの処理が実行中でないことを証明する仕組みと、その判定から中断保存を呼ぶ連携は共通applyの段階に残す。

端末時計が開始時刻より前に戻った場合は、虚偽の完了時刻を補わず検証エラーにする。順序番号は時計の前後に依存せず、端末に保存する新イベントごとに最大値＋1とする。順序番号の上限到達は書き込み前に拒否する。

## バックアップv9と復元

履歴が存在する場合、全22ストアを含むv9でエクスポートする。配色がなくても配色2表の空配列を含める。v9の読込みはv8相当の全検証に加え、履歴の配列・各レコード・UUID重複を検証する。v1〜v8に履歴を紛れ込ませた入力は拒否する。

履歴が存在しない場合は新ストアを出力から除外し、従来のv2〜v8の形式選択をそのまま保つ。入力は引き続きv1〜v8にも対応する。旧アプリは新しいv9を読み込めないため、新形式を復元する端末にはRC34以降のアプリが必要。

復元の最初に、新ストアを含む単一rwトランザクション内で現在履歴と入力履歴を照合する。

- UUIDが異なる履歴は追加する。
- 同じUUID・同じJSON内容は保持し、重複追加しない。オブジェクトのプロパティ順序は比較結果に影響しない。
- 同じUUID・異なる内容は、既存データのclearや書き込みより前に復元全体を拒否する。新しい日時・状態を優先して上書きすることもしない。
- 端末の既存履歴を削除・上書きせず、不足する入力履歴のみ追加する。
- 新しい文脈UUIDと最大順序番号＋1のrestoreイベントを、復元本体と同じコミットに含める。最後の履歴保存が失敗した場合も、復元本体と追加履歴をすべてロールバックする。

履歴を持つ端末へv1〜v8を復元する場合も、端末の履歴を保持して新文脈を記録する。v9入力は空の履歴配列でも新文脈を記録する。同じバックアップを繰り返し復元した場合、元履歴のUUIDは増えず、各回の復元イベントだけが追加される。

設計の具体化として、**端末にも入力にも履歴がなく、入力がv1〜v8の場合は復元イベントを作らない**。適用成功履歴を誤認する可能性がなく、まだ履歴を導入していない利用者のバックアップ形式を維持するためである。最初の明示的な取り込み開始時に初期文脈を採番する。v10移行自体では新文脈や履歴を作らない。

配色のv8／v9検証を共通化し、代表配色・仮配色・釣果の値コピーを保持する。旧v1〜v7の復元では、既存配色の内容と自然キーを保持してローカルID参照だけを解除する従来の規約を維持した。施設マージ・参照競合拒否・気象等の扱いも従来のままである。

## 現在のマスター状態との区別

文脈や履歴の先頭取得はイベントの識別用であり、「最新版適用済み」を返すAPIは追加していない。過去にsucceededが存在しても、復元後の現在データに不足があればPhase 1のplannerが差分を返す。

履歴はplannerの比較スナップショットへ追加しない。過去の成功履歴によって差分計算を省略する分岐や、復元後の自動再適用は実装していない。
