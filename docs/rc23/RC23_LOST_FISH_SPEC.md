# Fishing Log RC23 実装仕様書 v1.1 — バラシ記録

作成日: 2026-10-12
対象基点: RC22（PR #17 マージ後の `main`）
推奨ブランチ: `feature/rc23-lost-fish`
状態: **Codex開発指示用。未実装・未テスト・未反映。**

## 1. 目的

既存の「釣果登録」画面に、**キャッチ**と**バラシ**の結果選択を追加する。バラシとは、**魚をフッキングしたあと、取り込むまでに逃したこと**を指す。単なるアタリ、ミスバイト、フッキング前の空振りは対象外とする。

バラシはキャッチとは完全に独立した回数で集計し、バラシ時の距離感を **「沖」「手前」「キャッチ直前」** の3択で記録する。**使用ルアーはキャッチ・バラシの両方で記録できること**。釣行別・ルアー別にキャッチ数とバラシ数を比較できるようにする。

## 2. 絶対条件：RC22以前のデータ保護

- 既存の `trips`、`catches`、`myLures`、`lureManufacturers`、`lureSeries`、`lureModels`、`lureVariants`、`fishSpecies`、タックル、釣り場情報の既存レコード・ID・参照を変更・削除・再採番しない。
- 現時点の実機バックアップ基準値は、メーカー80、シリーズ147、モデル331、カラー2307、釣行5、キャッチ7、マイルアー4（ユーザーによるその後の変更があれば実機バックアップ優先）。巾着田 `tripId=10`、`catchId=11〜14`、既存ルアー参照も保持する。
- **既存の7件はすべてキャッチ扱い**。画面・集計・エクスポート・復元でキャッチ数7を維持する。
- カタログのRC19〜RC22取り込み機能と出典メタデータを壊さない。
- 手元の未追跡ファイルやバックアップを変更・削除しない。`git add -A` / `git clean` 禁止。
- データ移行、DBバージョン変更は必要性を検証してから行い、最小限に留める。新しいDexieテーブルが必要な場合は版上げが必要であり、勝手にDB v7固定を約束しない。バックアップ形式の後方互換性も検証する。

## 3. UI：既存の釣果登録画面を拡張

### 3.1 結果選択

- 既存の釣果追加／編集モーダル（`CatchModal` 等、実リポジトリで名称を確認）に **「キャッチ」「バラシ」** の選択UIを追加。デフォルトは **キャッチ**（従来の入力操作を維持）。
- **キャッチ**を選ぶと従来どおりの時刻・魚種・サイズ・レンジ・速度・アクション・ルアー・タックル等の入力ができる。
- **バラシ**を選ぶと距離区分の **沖／手前／キャッチ直前** が表示され、3択のいずれかを**必須**選択とする。未選択なら保存不可とし、理由を明示する。キャッチではこの項目を非表示／無効にする。
- バラシの記録時刻を保存する。魚種は分かれば入力可能だが**任意**。サイズは原則不要で、キャッチ用必須チェックがあればバラシでは適用しない。
- **使用ルアーはバラシでも既存のマイルアー／カタログ選択機能をそのまま利用**。ユーザーが選んだルアーID・モデル・カラーを保存。ルアー不明を無理に選ばせない（既存キャッチと整合する任意／必須ルールを確認し、明記）。
- 「前回と同じ」操作、時刻初期値、画面スクロール・タップ領域、iPhoneの小さな画面を維持。結果区分の切替で入力情報が意図せず失われないようにする。
- バラシで保存後、画面に**「バラシ登録完了」**など結果が分かる表示を行う。キャッチ数を増やさない。

### 3.2 釣行画面・履歴

- キャッチとバラシが一目で判別できる表示（例：`キャッチ 4匹／バラシ 2回`）。「総釣果」を単純に足して表示しない。
- 直近記録一覧に、結果区分、時刻、ルアー、バラシ時は距離を表示。距離は **沖・手前・キャッチ直前** の原文を表示。
- 既存キャッチ／追加バラシの**編集・削除**と、結果区分を切り替えた時の集計更新を検証する。変更・削除はユーザーの明示操作に限る。
- 魚種が不明なバラシも表示崩れ・例外なく処理できること。

## 4. 集計の定義

- **キャッチ数**: 結果が `catch` の記録の件数（従来レコードの結果未指定は `catch`）。
- **バラシ数**: 結果が `lost` の記録の件数。サイズ・魚種の有無には依存しない。
- **距離別バラシ数**: `lost` のうち距離が `offshore`（沖）／`near`（手前）／`landing`（キャッチ直前）の件数。
- **ルアー別キャッチ数**: 選択された同一ルアーに紐づく `catch` 件数。既存の `myLures.catchCount` などは **バラシを含めない**。
- **ルアー別バラシ数**: 同一ルアーに紐づく `lost` 件数。可能ならMy Lures画面に「キャッチ／バラシ」を並記し、両者が別集計であることを明示。
- 釣行全体の「合計接触回数」等を追加する場合でも、**キャッチとバラシの区別がなくなる表示は不可**。RC23の主目的は分離集計。
- キャッチ・バラシの両方で、カタログのモデル・カラーを特定したルアーは所有しているものとして扱い、未登録ならマイルアーへ自動登録する。既存の実所有個体があれば再利用し、重複登録しない。手入力だけのルアーは自動登録しない。
- 自動所有登録と記録保存は単一トランザクションで行い、途中失敗は両方ロールバックする。編集・削除ではマイルアーを自動削除しない。結果切替でも既存所有を再利用する。
- RC22までの既存マイルアーのID・参照・登録状態を一括変更しない。未確認・placeholder・使用停止中の個体の扱いは従来の実所有判定を維持する。

## 5. データモデル方針（Codexがコード調査後に決定）

推奨は、既存 `catches` のキャッチ記録を壊さない構造で**同じ釣行に紐づくイベント**を保存すること。以下のいずれかを実装し、採用理由を報告する。

**案A：既存 `catches` に任意フィールドを追加（第一候補）**

- `resultType?: 'catch' | 'lost'`（既存レコードで未設定の場合は `catch`）
- `lostDistance?: 'offshore' | 'near' | 'landing'`（`lost` の場合のみ必須）
- 既存レコードをまとめて上書きしない。旧データ読み取り時のデフォルト処理で後方互換にする。
- `catchCount`、レポート、履歴、バックアップ、釣行終了処理など**catchesの全参照元**を洗い出し、バラシが既存のキャッチ数へ混ざらないようにする。

**案B：独立したバラシ記録テーブル**

- 既存コードへの副作用が大きい場合のみ採用。`tripId`、時刻、距離、使用ルアーなどを保存し、釣行履歴上ではキャッチと時系列統合。
- 新テーブルのDexieバージョン管理、JSONバックアップの書き出し・復元、古いJSON互換、参照整合性、トランザクションを必須とする。

**いずれの案でも**、既存キャッチのIDおよび使用ルアー参照を維持し、キャッチとバラシ双方の保存・編集・削除・バックアップを実機相当テストで検証すること。

## 6. データ入力・変更時の詳細条件

- バラシ距離は3択以外の値を受け付けない。キャッチに距離のゴミデータを保存しない。
- バラシをキャッチへ変更した場合、必要に応じキャッチ固有項目の入力確認を行う。バラシ距離は消去または対象外として処理する。
- キャッチをバラシへ変更した場合、バラシ距離選択が必須。キャッチ数は1減り、バラシ数は1増える。
- 保存をキャンセルした場合はDB書き込みなし。処理失敗時は中途半端な記録を残さない。
- 保存後の集計／一覧は再ロードなしで更新できること。2重タップによる重複登録を防止する。
- ルアーが削除・非表示・名称変更された場合は既存参照とスナップショット方針を尊重し、記録が消えないこと。

## 7. バックアップ・復元

- RC22までの旧バックアップJSONを復元しても既存レコードはすべて `catch` として扱う。
- RC23の新しいバックアップはバラシの結果区分・距離・ルアー参照を完全に保存し、復元できること。
- バックアップ形式の `version` を変える場合、旧形式と新形式の互換性・受入条件を記録。形式を変えない場合も新規任意フィールドの保存・復元を確認。
- **既存の実機バックアップ原本は書き換えない**。新しいテストデータは複製環境で利用。

## 8. テストと受入基準

1. 旧RC22相当データ（キャッチ7、マイルアー4、カラー2307等）をロードし、**キャッチ7／バラシ0**。既存ID・全既存フィールドが一致すること。
2. 釣行でキャッチ1件を登録 → キャッチ+1／バラシ+0。
3. 同じ釣行で「沖」「手前」「キャッチ直前」のバラシを各1件、**使用ルアー付き**で登録 → キャッチ増分0／バラシ+3、距離別各1。
4. 魚種不明・サイズ未記入のバラシが保存・表示できること。
5. バラシのルアー別数が正しく、既存のマイルアーの**キャッチ数に加算されない**こと。
6. 釣果・バラシの編集、結果切替、削除を検証し、釣行別・距離別・ルアー別が即時再計算されること。
7. キャンセル、必須距離未選択、二重操作、保存中エラーで不正なレコードが増えないこと。
8. バックアップ／復元前後でキャッチ・バラシ・ルアー参照・距離・旧データの内容が一致すること。
9. RC19〜RC22カタログプレビュー／追加の退行なし。既存釣果7件・マイルアー4件・全カタログと魚種・タックル・釣り場データの更新／削除ゼロ。
   記録で未登録のカタログ色を使用した場合の新しい所有個体の追加は許可する。キャッチ・バラシで同じ色を繰り返し使用しても追加は1個体だけで、手入力では追加0。編集・削除・結果切替で既存所有を自動削除しない。
10. desktop/mobile E2E、オフラインPWAテストを実施。iPhone Safari PWAの**実機試験はデプロイ後、バックアップを取ってから別途**実施。
11. `npm.cmd run build`、既存単体テスト・E2E・オフライン・型チェックを実行して報告。既存の失敗とRC23で新規発生した失敗を区別。

### 実機での確認シナリオ

- 実機バックアップ取得 → カタログ2,307色・釣果7・所有4等の最新数値を確認。
- RC23デプロイ後、iPhoneホーム画面PWAを再起動。キャッチ登録画面に結果選択があり、従来のキャッチ登録は従来どおり機能する。
- 別のテスト用釣行でバラシ3区分を試し、ルアー選択・別集計・編集・再起動後の永続化・オフライン動作を検証。
- 実機の反映前後バックアップを比較し、既存全レコードの変更・削除がないことを確認。
- **テスト用データを実釣履歴に混ぜない**。本番環境のテスト用釣行・バラシの片付けはユーザー操作または事前同意のもと実施し、既存レコードを自動削除しない。
