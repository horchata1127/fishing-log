## 調査範囲と安全条件

現行仕様とRC32の推奨案を分けて記載する。DBバージョン・バックアップ形式・新規フィールド名は、現行仕様と明記したもの以外は設計案である。

- 既存データの削除・初期化・自動復元は行わない。
- バックアップJSONは直接編集しない。
- 視覚辞書の導入・推定・修正によって所有情報を追加・変更しない。
- 既存マスターのID・名称・親子関係と、釣行・釣果・イベント等を保持する。
- 今回は端末DBを開いていない。iPhoneの実DBバージョン・件数・状態は未確認。
- リモートとの最新一致は未確認。ローカルRC31を基準にしている。
- 今回の調査ではビルド・テストを実行していない。過去の検証結果は今回の実測と区別する。

## RC32の確定方針

- 基本48色と特殊属性12種類。
- 複数色選択と簡易リアルタイムプレビュー。
- スプーンは表裏、ミノー・クランクは背・側・腹。
- 公式カラー不明でも仮カラーで釣果登録。
- 公式カラーと視覚カラーを永続的に紐付け。
- 視覚カラーから公式カラーを逆引き検索。
- 釣果登録時に色アイコンを表示。
- 公式カラー約2,899件から可能な限り仮配色を自動生成。
- 自動推定は公式写真を優先し、次にカラー名称を利用。
- ユーザーが修正した配色は自動推定で上書きしない。
- 釣果の配色スナップショットを保持。
- オフライン・バックアップ復元に対応。
- 現場で素早く操作できることを優先。

48色・12属性の具体的な一覧、固定ID、表示順は未確定のため、最初の設計段階で決定する。

## 1. Dexieのスキーマと既存DBバージョン

根拠：[database.ts](../../src/db/database.ts)。依存宣言は `dexie: ^4.4.6`。ライブラリのバージョンとDBスキーマのバージョンは別のもの。

DB名は `FishingLogDatabase`、コード上の最新Dexieバージョンは **8**、全19テーブル。端末が実際に開いているDBの状態を確認した値ではない。

| catches | `++id, tripId, caughtAt` |
| lureManufacturers | `++id, &name` |
| lureSeries | `++id, manufacturerId, name` |
| lureModels | `++id, seriesId, name` |

`++`は自動採番、`&`は一意索引。シリーズ・モデル・カラーに自然キーの一意制約はなく、取り込み処理が重複を検出する。索引にないフィールドもレコードには保存される。

|---|---|
| 1 | trips・catches |
| 2 | tripsの索引拡張 |
| 3 | ルアーマスター4種・所有ルアー |
| 4 | tripEvents |
| 5 | タックル4種 |
| 6 | fishSpecies |
| 7 | facilities・zones・appMetadata |
| 8 | 気象3種 |

直近の拡張は既存ストアを保持した追加方式。DB接続には `versionchange` 時の接続終了と `blocked` の通知がある。**DBバージョン8とバックアップ形式v7は別の番号体系**。

## 2. 釣果登録・編集時のルアーと公式カラー選択

根拠：

- [CatchModal.vue](../../src/components/CatchModal.vue)
- [catchRegistration.ts](../../src/utils/catchRegistration.ts)
- [App.vue](../../src/App.vue)

選択は `LureSelection` の3経路。

| 経路 | 保存内容・動作 |
|---|---|
| owned | myLureIdから公式カラーを解決。所有ID・カラーID・表示名を釣果に保存 |
| catalog | モデル→公式カラーを選択。実所有個体がなければmyLuresも追加 |
| manual | lureName・lureColorを保存。マスターや所有情報は追加しない |

カタログ・所有候補はメーカー、分類、メーカー名・シリーズ名・モデル名・色名を含む文字列で絞り込める。カタログ経路はモデルを選んでからカラーを表示する。最近使用したルアーは最大5件。「前回と同じ」もある。

所有候補は `active === true` かつ `ownershipStatus === 'owned'`。所有状態未設定は `unverified` として扱う。

編集時はルアーを選び直さなければ既存の参照ID・名称を保持する。配色フィールド、配色スナップショット、色による検索はない。

RC32では仮カラーを独立した選択状態にし、モデルだけ特定できる場合も記録できるようにする。辞書の整備・推定ではmyLuresに書き込まない。既存のカタログ選択による所有登録は釣果登録の仕様なので、辞書機能の保存と混同しない。

## 3. 公式カラーマスターとモデル・メーカーの関連

```text
lureManufacturers
  └─ lureSeries.manufacturerId
       └─ lureModels.seriesId
            └─ lureVariants.modelId
                 └─ myLures.variantId
```

公式カラーの実体は `lureVariants`。ただし手入力でも行を作成できるため、全行が公式確認済みとは限らない。

`LureVariant` は `id / modelId / colorName / catalogEvidence?` を持つ。証跡にはrevision、出典区分、メーカー・小売URL、JAN、原名、任意のカラーコード・重量・全長・浮力・ラトル・製品URLを保持できる。証跡のない既存行もある。

同じカラーコード・色名でも異なるモデルでは別バリエーション。モデル・メーカーをまたいだ自動統合はしない。公式表記は保存し、比較時だけ正規化する。

### 画像の現状

[rc22Catalog.tsの生成データ](../../src/data/rc22Catalog.ts)には非空の画像URLが35件ある。一方、[RC22の追加処理](../../src/utils/rc22Catalog.ts)は画像URLをDBへ保存しておらず、現行の `LureVariant` 型にも画像フィールドはない。

約2,899色全体の写真対応表は、現行DB構造だけでは得られない。写真優先の推定には、画像とモデル・カラーの対応資料を別途整える必要がある。URLが記載されていることと、現在画像が取得できること・配色解析に適することは別であり、今回外部画像の確認は行っていない。

## 4. ルアー分類の判定方法

`lureModels.category` を直接使う。名前・形状からの自動分類はない。未設定は表示上「その他」とする。

分類は `スプーン / クランク / ミノー / トップ / バイブレーション / その他`。

RC31の分類はPowaleが「トップ」、GANOFFが「その他」、Galetteが「クランク」。GANOFFを描画の都合だけでクランクへ変更しない。

RC32では部位構成を別の `layout` として保持する案を推奨。

| 分類 | 初期の部位構成案 |
|---|---|
| スプーン | 表・裏 |
| ミノー・クランク | 背・側・腹 |
| トップ・バイブレーション・その他・未分類 | 共通配色から開始。必要なら部位構成を選択 |

部位構成を変えても既存カテゴリは変更しない。既存のカタログ取り込みでカテゴリが更新される場合に備え、保存済み配色のlayoutを都度再判定しない。

## 5. バックアップJSONのエクスポート・復元

根拠：[backup.ts](../../src/utils/backup.ts)、[App.vue](../../src/App.vue)。

- `createBackup()`：読み取りトランザクションでテーブルを収集。
- `exportBackup()`：JSONをダウンロード。
- 出力は内容に応じてv2〜v7、入力はv1〜v7に対応。
- `validateBackup()`：書き込み前に形式・日時・ID重複・親参照・所有とカラーの整合等を検証。
- `importBackup()`：検証済みデータを単一書き込みトランザクションで復元。

**現行の復元は置換処理**。釣行・釣果・ルアー・魚種・タックル等をclearして再登録し、気象も置換する。施設・エリア・マスター情報は競合保護付きでマージする。画面の明示確認後にのみ実行される。

RC32導入に復元処理を使用しない。本調査でも実行していない。

推奨はバックアップ形式v8を追加し、新テーブル・配色スナップショット・辞書版・編集保護状態を検証対象にすること。旧v1〜v7の読み込みは維持する。

旧形式を明示的に復元する場合、新規辞書の扱いを決める必要がある。古い数値IDが別のカラーを指す可能性があるため、既存配色を数値IDだけで再接続しない。自然キーを併記して照合し、不一致・曖昧な対応は未関連として保持する。復元前に件数と競合を提示する設計が望ましい。復元による既存データの置換仕様をRC32でどう扱うかは、導入時の無破壊マイグレーションとは分けて決定する。

## 6. RC30・RC31の差分取り込み方式

根拠：

- [rc30Catalog.ts](../../src/utils/rc30Catalog.ts)
- [rc31Catalog.ts](../../src/utils/rc31Catalog.ts)
- [LureCatalogImportPanel.vue](../../src/LureCatalogImportPanel.vue)
- [RC31検証記録](../rc31/RC31_VALIDATION.md)

1. 既存4マスターを読み、追加・保持・保留を計画。
2. 画面で事前照合し、差分CSVを保存可能。
3. 明示的な追加操作時に変更前バックアップを出力。
4. 比較トークンでプレビュー後の変更を検出。
5. 4マスターの単一トランザクションで追加。

既存ID・名称・所有情報は変更せず、競合・複数候補は保留する。RC30は既存メーカーを必要とし、RC31はPALMSメーカーの追加にも対応。RC31はモデル内コードを優先し、コードなし既存カラーは名称照合も行う。起動時・復元時の自動追加はない。

初期カタログJSONの処理は [importLureCatalog.ts](../../src/importLureCatalog.ts) にある。親のIDを対応付けて依存順に登録し、入力の固定IDをそのまま新規採番に使わない。既存モデルのカテゴリだけ更新する経路もあるため、RC32の辞書適用でその処理を無条件に流用しない。

### 約2,899色の根拠と限界

RC31検証記録では、指定件数と同じ合成データの2,816色へ83色を追加し、2,899色となった。2回目は追加0件。個人データと既存マスターの保持を検証したと記録されている。

実バックアップ本体ではなく合成データでの過去の結果であり、端末の実件数を保証しない。RC32では実際に存在するカラー行を対象に照合し、2,899件を満たすための架空行追加はしない。

## 7. RC32の推奨データ構造と導入方法

### 追加方式

Dexie v9で新テーブルだけを追加する。既存19テーブルのID・索引・レコードを導入時に書き換えない。旧釣果へ配色を一括補完しない。

| 保存先（名称は案） | 内容 |
|---|---|
| `src/data/visualColors.ts` | 基本48色・特殊属性12種の固定ID、名称、表示値、辞書版 |
| `lureVisualProfiles` | 公式カラーIDを主キーとする配色、推定根拠、編集保護状態 |
| `temporaryLureColors` | UUIDを主キーとする仮カラー、任意モデル参照、配色、後日の公式カラー紐付け |
| CatchRecordの任意フィールド | 仮カラー参照、必要に応じモデル参照、配色スナップショット |

固定辞書のIDは表示順に依存させず、将来の版でも意味を変えない。公式カラーのローカルIDと、異なる環境間での対応確認に使う自然キーを区別する。

### 共通の配色値

以下は概念例であり、まだ実装コードではない。

```ts
type VisualAppearance = {
  version: 1
  paletteVersion: 1
  layout: 'spoon' | 'body' | 'generic'
  regions: {
    [region: string]: {
      colors: string[]
      attributes: string[]
    }
  }
}
```

- spoon：front / back（表・裏）
- body：dorsal / side / belly（背・側・腹）
- generic：whole（共通）
- colorsは選択順を保存し、先頭を主色とする案。
- attributesは特殊属性ID。色と属性を分離する。
- 実装時はlayoutごとの型に分け、使用できる部位を検証する。
- 分からない部位は未設定にする。未設定・透明・白などを区別する。

### 公式カラーとの対応情報

- ローカルのvariantIdと、復元・配布データ照合用の自然キー。
- 配色値と状態（未設定・推定・ユーザー確認済み等）。
- origin（ユーザー／写真推定／名称推定）。
- userEdited、編集リビジョン、更新日時。
- 推定器の版、根拠URL、利用時の画像ハッシュ等。
- 部位ごとの根拠・確信度。写真と名称を併用した場合も記録できる構造。
- 逆引き用のcolorIds・attributeIds。

colorIds・attributeIdsには複数値索引を設ける案。これらは配色値から生成する派生項目とし、更新・復元時に整合を検証する。まず色で候補を取得し、部位・属性・モデル等で絞り込む。

メーカー＋シリーズ＋モデル＋モデル内カラーコードを基本に照合し、コード欠落時は原名・別名も用いる。同一候補が複数ある場合は自動対応させない。

### ユーザー編集保護

自動適用時にトランザクション内でuserEditedとリビジョンを再確認する。プレビュー時だけの判定では、編集中の変更を保護できない。ユーザー修正済みの配色は自動推定で上書きしない。新しい推定は必要なら別候補として提示する。

### 釣果のスナップショット

登録時の配色値、辞書版、部位構成、推定・確認状態を値としてコピーする。辞書改訂後も同じ見た目を再現できるよう、描画用色値も保持する。

- メモ等だけの編集では配色を再生成しない。
- 「前回と同じ」は前回の配色を再利用する。
- 公式カラーの辞書を修正しても過去釣果は変えない。
- 仮カラーを後日公式カラーへ紐付けても、過去の配色を無断で置換しない。
- 旧釣果へ当時の配色を推測して保存しない。未記録として表示できるようにする。

## 8. 現場操作と自動配色

### 操作案

1. 最近使用・所有ルアーを優先表示。
2. 基本色をタップすると候補とプレビューを即時更新。
3. 複数色検索は「選択した色をすべて含む」を基本とする案。
4. 候補が特定できなければ、その配色で仮登録して釣果保存。
5. 詳細な部位・特殊属性の調整は必要なときだけ開く。

選択部位とプレビューを同じ画面に置き、色名入力を必須にしない。色だけに依存しないラベルと選択表示を付ける。プレビューと釣果アイコンは共通SVG部品にし、通信なしで描画する。

### 自動配色の生成案

1. モデル・カラーとの対応が確認できる公式写真を優先。
2. 写真が使えない色や未確認項目をカラー名称で補完。
3. 根拠の不足する部位・属性は未設定として残す。
4. 推定済みデータを同梱し、端末の自然キーから既存IDへ対応付け。
5. 事前照合で追加・保持・保留・ユーザー編集保護の件数を提示し、差分適用。

推定は開発時のバッチ処理を基本にする。釣果登録中に画像取得や推定完了を待たせない。写真が得られなくても名称推定と同梱済み配色で利用可能にする。

写真の背景・反射・複数商品の混在を識別する必要がある。写っていない裏面や腹、写真だけで分からない特殊属性を確定しない。自動生成できた件数と、部位別の未推定件数を分けて報告する。

### オフライン

根拠：[vite.config.ts](../../vite.config.ts)、[pwa.ts](../../src/pwa.ts)。現行PWAはHTML・JS・CSSを事前キャッシュし、runtimeCachingは空。更新はprompt方式で、他画面や入力状態を保護する仕組みがある。

配色をJS同梱データとSVGで表示する構成なら既存方式を利用できる。写真そのものも圏外で表示する場合は追加のキャッシュ・容量・配布設計が必要。配色辞書と釣果スナップショットはIndexedDBとJSONバックアップで保持し、外部画像の可用性に依存させない。

| リスク | 対応 |
|---|---|
| 写真・独自色名による誤推定 | 根拠・確信度・未確認状態を持ち、不明部位は空のまま保存 |
| 推定処理とユーザー編集の競合 | 保存直前のトランザクションで編集保護とリビジョンを再確認 |
| 旧バックアップ復元後のID再利用 | 数値IDだけで再接続せず自然キーで照合。曖昧な配色を未関連として保持 |
| 分類未設定・特殊形状 | categoryとlayoutを分離し、共通配色から記録可能にする |
| 異なる仮配色が同じ名前で集計される | 仮カラーIDや保存時配色を考慮した一覧・集計キーを設計 |
| 初回適用の長時間化 | 推定は事前生成。端末適用は再開可能な小分け処理にする |
| キャッシュ・容量 | 写真と配色値の保存を分離。通常操作は配色値だけで成立させる |
| 将来の辞書変更で過去の見た目が変わる | 辞書版と描画値を釣果スナップショットに保持 |

## 12. 実装時の検証計画と未確定事項

### 検証計画

- v8以前からv9への更新で、既存19テーブルの件数・ID・内容が保持されること。
- 配色差分を2回適用し、2回目の追加0件・自然キー重複0件となること。
- ユーザー修正済み配色が自動推定で変化しないこと。競合時も保護されること。
- 仮カラー保存・辞書編集でmyLuresが増減しないこと。
- メモ編集・辞書改訂・公式カラーへの後日紐付けで過去の配色が変わらないこと。
- 「前回と同じ」、最近使用、旧釣果編集、仮カラー別集計を確認すること。
- 旧v1〜v7の読み込み、新v8の全データ往復、不正参照の拒否、復元後の誤紐付け防止を検証すること。
- 書き込み失敗時のロールバックと、中断後の再適用を検証すること。
- 圏外での登録・検索・再起動とiPhone Safari実機の操作性を確認すること。
- `npm.cmd test`、`npm.cmd run build`、必要なE2E・オフラインテストを実行すること。

検証は隔離したテストDB・合成データで行い、ユーザー端末の削除・初期化・自動復元は行わない。
