# RC43 NOA共通カラー写真・商品ページリンク

NOAシリーズのカラー選択に、確認済みのローカル写真と、保存許可を確認できない場合の個別商品ページリンクを追加した。NOA 1.8g、NOA Jr.、NOA Sなどの同じ共通色は1組の写真・リンクを共有する。既存688カラーとそのID、配色SVG、所有、釣行・釣果を変更・生成しない。

調査範囲と全色対応は [RC43_RESEARCH.md](RC43_RESEARCH.md)。既存実モデル8件・688行を94共通色に分け、33共通色に城峰釣具店の個別商品URLを同梱した。実物写真の同梱は0件。写真の利用許可を確認できないため、自動ダウンロード・ホットリンク・Service Workerによる画像キャッシュは行わない。

## 利用方法

1. 「ビジュアルカラー辞書」でNOAのモデル・カラーを選び、「カラー写真を管理」を開く。
2. 自分で撮影した写真、または保存・表示・自分のバックアップへの利用が許可された写真を選ぶ。
3. 表面／裏面／その他、NOAシリーズ共通／モデル専用を指定する。写真の権利と、カラー・面が正しいことを確認して保存する。
4. 釣果の通常ルアー選択または「カラーチェンジ」で写真から選ぶ。写真はタップで拡大でき、表裏の切り替え、写真／SVG切り替え、所有のみ、名前・番号検索に対応する。

確認前の写真も管理画面に保存できるが、釣行中の写真候補には使わない。写真の差し替え・削除・確認状態変更は写真管理内で行う。共通色にどのモデルが含まれるかを一覧で確認できる。

写真がない場合は従来のSVGを表示し、採用済みのリンクがある色には「写真を見る」とショップ名・通信が必要なことを表示する。別タブで開くため入力中のメモ・選択は残る。リンクなし、圏外、リンク切れでもカラーを選べる。元々SVG配色がない色は汎用スプーンアイコンへ戻る。

## 保存方式・表示順位

DBを内部版11から12へ更新し、次の空テーブルだけを追加した。既存テーブルへのupgrade書き込み、既存IDの変更、起動時のカラー・所有シードはない。

| テーブル | 主な内容 |
| --- | --- |
| sharedLureColors | 共通ID、NOAファミリーキー、名称・番号・別名、照合状態、代表画像ID、単独の商品URL、出典、利用可否、権利状態、確認日 |
| lureColorPhotoLinks | 既存variantIdと共通ID、メーカー・シリーズ・モデル・カラーの完全な名前識別子 |
| lureColorPhotos | 複数写真のメタデータ。共通ID、モデル専用時の識別子、面、Blobのハッシュ、出典、許可・確認状態、更新日時・revision。モデル専用URLもここに1件保持 |
| lurePhotoBlobs | SHA-256を主キーにしたBlob、幅・高さ。モデルや重量をまたいで同じバイナリを再利用 |

既存ではNOA／NOA Jr.／NOA Sが別seriesIdであるため、共有単位は既存seriesIdを置き換えず `rodio-craft:noa` というファミリーキーで表す。名寄せは `noaPhotoCatalog.ts` に集約し、他メーカーやMOCAには適用しない。テーブル形式は将来ほかのファミリーにも拡張できる。

表示順位は選んだ面について、確認済みモデル専用ローカル写真→確認済み共通ローカル写真→モデル専用の確認済み商品URL→共通の確認済み商品URL。ローカル写真が使えない場合にSVGとリンクを併記する。ローカル写真が使える間はリンクをカードに並べない。リンクは共通色につき1件で、モデル専用も同じ識別子に対して1件だけ保存する。

写真の保存許可と、写真がそのカラーを示すかの確認は別項目。URLの確認状態も写真の確認とは独立させ、写真を登録しただけで未確認リンクを確認済みにしない。写真の読み込み失敗時は、別の使用可能なローカル写真、SVG・単独リンクへ順にフォールバックする。

旧JSON復元後に数値IDが別ルアーへ再利用されても、保存したモデル・カラーの完全な名前識別子が一致しない専用写真は表示しない。共通写真は重量に依存しない共通色IDで解決する。写真バックアップの関連情報を取り込む際も、端末の現在のカタログへ名前識別子で関連付け、持ち込まれた数値IDだけを信用しない。

## 画像・オフライン

- ローカルファイルのみ受け付ける。JPEG／PNG／WebPの署名と実寸を確認。入力15MB・4000万画素以下。
- ブラウザで長辺1280px以下のJPEGへ縮小し、保存時は2MB以下。Canvas出力により元ファイルのEXIF等を持ち込まない。HEICはJPEGへ変換が必要。
- Blobハッシュの照合は書き込みトランザクション前に実施し、写真・関連・Blobを原子的に保存する。容量エラーでカタログや写真が部分保存されない。
- 表示時に全Blobを読み込まず、表示対象の写真だけをIntersectionObserverで読み込む。Object URLは差し替え・画面終了時に解放する。
- 写真メタデータとBlobはIndexedDBに保存され、保存済み写真は圏外のブラウザ再起動後も表示できる。
- 画像・商品URLをアプリからfetchしない。リンクは `target="_blank" rel="noopener noreferrer"`。既存のPWA静的キャッシュ規則は変更しない。

## バックアップ

通常の釣行JSONバックアップv1〜v12（v10を含む）の形式・インポート／エクスポート処理は変更しない。内部DB版12とは別の番号体系。

写真管理の「写真バックアップを保存」で `fishing-log-lure-photos.json` を別途保存する。共通色・関連・ローカル写真・出典・リンクを含み、Blobはハッシュごとに1回だけBase64化する。形式は `fishing-log-lure-photos` v1。1ファイル150MBまで。

復元は通常の釣行JSON、写真JSONの順を推奨する。写真JSONは既存の釣果・所有情報を書き換えない。同じ写真JSONを2回読んでも写真やBlobが増えない。画像ハッシュ・寸法・参照・利用条件を検証してから一括保存し、同IDの写真やユーザー編集済みリンクと内容が競合すると全取り込みを拒否する。画像ID・表示可否など再計算可能な情報の差は、既存写真を上書きする理由にはしない。

通常の旧JSONに写真がなくても端末の写真を削除しない。ホームにも写真を別保存する案内を追加した。明示的な開発用「全データ削除」は新しい写真テーブルも削除する。

## データ保全・テストの変更

写真登録・閲覧・リンク閲覧だけでmyLuresやcatchesを作成しない。釣果を実際に保存するときの既存の所有登録・カラーチェンジ動作は維持する。

テスト用のv10データに、手動編集済みSVG配色（revision 7）、所有・釣果を入れて保全を確認した。2026-11-21実バックアップも隔離IndexedDBで復元し、写真登録前後の全既存テーブル・ID・値を比較した。原本のSHA-256は不変。

既存の移行テストでは現行DB版・テーブル数を12／27へ更新し、既存ストアの全値・インデックス保持の検証は残す。旧JSONの回帰テストは、新規写真ストアが空であることを検証してからJSONに含まれない独立テーブルを除外して比較する。旧形式で省略される空のareaMapsも同様に明示確認する。本番のJSON仕様を変えてテストを通す変更は行わない。

検証の最終結果は [RC43_VALIDATION.md](RC43_VALIDATION.md)。iPhone Safari実機は未検証。モバイル自動テストはChromiumのiPhone 13条件であり、実機Safariの保証に置き換えない。
