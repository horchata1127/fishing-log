## 1. 目的・スコープ

2026-10-11 巾着田での初実釣（キャッチ4匹、バラシ約2匹）を受け、(P0) 保存済み釣果を後日訂正可能にする。(P1) 川魚・バスの魚種を選択可能にし、ルアーにニュードロワーの HUNT GRANDE 1.3g を追加する。余裕があれば (P2) フッキング後のバラシを記録する。

**必須条件**: 保存済み釣果、釣行、所有ルアー、マスターのIDと関連を維持する。既存データの全消去・再採番・無断自動上書きは禁止。

## 2. 現状のコードを踏まえた設計前提

- `src/db/database.ts`: `CatchRecord`、魚種 `FishSpecies`、Dexie DB定義。**DBスキーマは v7 まで存在**（v6が魚種、v7が施設/エリア）。
- `src/utils/catchRegistration.ts`: `registerCatch` と `registerSameAsPrevious` は**新規追加用**。そのまま編集に流用すると新規行が増えるため、編集専用の更新処理を追加する。
- `src/components/CatchModal.vue`: 既存の釣果入力 UI。編集時は既存値で初期化し、保存/キャンセルを分岐する。
- `src/App.vue`: 釣果一覧ロード、新規登録、モーダルの状態管理。
- `src/components/FishingScreen.vue`: 釣果表示と編集開始アクションを追加する。
- `src/utils/fishSpecies.ts`、`src/data/fishMaster.ts`: 初期魚種/登録/選択。既存グループは `ニジマス`、`ブランドマス`、`イロモノ` のみ。新グループ追加に合わせバリデーション・UI・バックアップ互換性を確認する。
- `src/utils/backup.ts`: 既存バックアップ復元の全テーブル検証あり。破壊的操作前にエクスポートして復元確認する。
- 付属ZIPには多数の未コミット変更が存在する。**ZIPのコミットHEADのみをGitHubからチェックアウトしてもこの状態は再現しない**。ベースをすり替えない。

## 3. P0 保存済み釣果の編集

### 3.1 UI

1. 釣果一覧の各行に「編集」操作を表示。iPhoneでもタップできる当たり判定（目安44×44 CSS px）。
2. 操作で編集モーダルを開き、選択した `CatchRecord` の保存済み値をすべて初期表示する。
3. 編集対象: 釣果日時、ルアー（所有/カタログ/手入力）とカラー、魚種、全長、レンジ、速度、アクション、タックル、釣行内エリア、メモ（表示・保存が既存で対応する場合）。
4. 「保存」「キャンセル」。キャンセルはDB更新なし。二重タップ/多重保存を防ぐ。成功後は一覧と集計を再読込。
5. 終了済み釣行も過去データ訂正の対象とする。登録の禁止条件（`trip.endedAt`）と編集の許可条件を分離する。
6. 編集で `caughtAt` を変更した場合、正しい日時順に再表示。保存値にない任意項目を勝手に初期値で埋めない。

### 3.2 データ・更新処理

- `updateCatch(catchId, editInput, lureSelection)`（仮名）を `src/utils/catchRegistration.ts` または専用ユーティリティに実装。
- 単一 Dexie `rw` トランザクションで対象釣果の存在と親釣行IDを確認し、ルアー参照・魚種参照・エリア・タックルの検証後に **`db.catches.update(id, patch)`**。`id` と `tripId` は変更しない。
- 使用ルアーを切替えたら、`lureId`、`lureVariantId`、`lureName`、`lureColor` を**整合する組**にする。以前の参照値は残さない。マスター選択時に必要な所有ルアー行を生成する処理は同一トランザクションで行う。
- 魚種切替時は `fishSpeciesId`、`fishSpecies`、`fishSpeciesGroup` を現行マスターの情報で再スナップショット化。未設定に戻す場合は関連3項目すべてをクリアする。
- `tackleSnapshot` と `locationSnapshot` も変更後の参照に合わせ更新/クリアする。未変更のときは保持する。
- `null` / `undefined` / フィールド削除のDexie挙動を考慮し、値の消去が確実に永続化される実装・テストとする。
- `caughtAt` は有効な日時、魚の全長は入力時だけ正数。親釣行と参照の整合を検証。失敗時はロールバック。
- 編集だけなら DB v7 のままで実装可能。スキーマ変更を入れる場合のみ v8 を追加し、v1–v7は書き換えない。

### 3.3 受入条件

- 既存の1件を編集しても総釣果件数は変化しない。ID/釣行IDが維持される。
- ルアー・色・魚種・日時変更後、画面と再起動後の保存値が一致する。
- 選択解除や手入力への切替時に古いルアーID/魚種IDが残らない。
- キャンセル/保存失敗時には変更なし。
- 終了済み釣行の記録も修正できる。

## 4. P1 魚種マスター拡充

### 4.1 追加候補

- `川魚`: カワムツ、オイカワ、ウグイ、ヌマムツ、アブラハヤ、タカハヤ、ムギツク（将来追加候補：モツゴ、コイ、フナ類など）
- `バス`: スモールマウスバス、ラージマウスバス
- 既存25件のトラウト/ブランドマス類は維持。ユーザー独自の魚種や非表示設定も維持。

### 4.2 実装要件

- `fishGroups` に `川魚` と `バス` を追加し、型・登録検証・魚種ピッカーの分類表示・バックアップ検証を揃える。
- Excel/CSVの魚種IDと重複を照合し、**新しい安定ID**を付与。既存IDを再利用・再採番しない。正式登録前に列と候補名の照合結果を残す。
- 既存の `registerInitialFishSpecies()` の「不足分追加・ユーザー編集温存」方針を維持。起動ごとの強制更新や既存釣果の魚種一括補完は禁止。
- 川魚/バス釣行時にニジマスを暗黙の初期選択にしない。未選択で登録できるようにするか、釣法ごとの適切な初期値を別途検討する。
- 画像だけで魚種が断定できない場合は「未設定」で登録して後から編集可能とする。

### 4.3 受入条件

- 川魚7種＋バス2種が選択・保存・再読込・バックアップ復元できる。
- 既存グループも従来どおり選択できる。
- 同じマスターを複数回取り込んでも重複しない。

## 5. P1 ルアーマスター拡充

### 5.1 対象と照合ルール

- メーカー: **ニュードロワー（New Drawer）**、既存メーカーIDを再利用。
- 追加確認対象: **HUNT GRANDE 1.3g**（通常の HUNT とは別シリーズ）。重複している場合は新規追加しない。
- 実釣時に使用したカラー呼称: **シルバー**（3匹）、**オレキンブラックゴールド**（1匹）。メーカー公式カラー名・色コードとの対応は要照合（仮称のまま既存データを上書きしない）。
- 公式掲載色は原則すべて収録する方針を継承。ただし当該モデルに存在しないカラーや表記ゆれを混入させない。
- RC18のカタログ原本と実機マイルアー情報を突き合わせ、メーカー→シリーズ→モデル→カラーの既存IDを再利用して不足分だけ追加。

### 5.2 受入条件

- `HUNT GRANDE 1.3g` を検索/選択し、正しいカラーで釣果登録・編集できる。
- カタログの再取込でも重複・所有数の水増しがない。
- 既存 `myLures` / `catches` のIDは変わらない。

## 7. P2 バラシ記録（時間が許せば）

### 7.1 定義

**魚がフッキングしたと認識でき、その後キャッチ前に外れた事象**。単なるアタリ、未フッキング、石・障害物接触は含めない。キャッチと混同しない。

### 7.2 最小仕様候補

- `釣果（キャッチ）` と `バラシ` を区別できる記録種別を導入（例: `CatchRecord.outcome?: 'caught' | 'lost'`）。旧レコードはフィールド欠落時に `caught` 扱い。
- バラシは時刻とルアー・カラーなどを任意記録可能。魚種/全長は省略可。
- トップ画面の **キャッチ数にはバラシを加算しない**。バラシ回数とキャッチ率は別表示（母数に記録漏れがあり得ることを示す）。
- 既存集計・所有ルアー釣果数・バックアップの整合性に影響するため、影響範囲確認後に実装。無理ならRC20に繰り越す。

## 8. データ保護・テスト

### 8.1 作業開始条件

1. iPhoneの実釣DBを、現行アプリの**エクスポート機能**でバックアップし、安全な場所に保存。
2. バックアップのバージョン・件数・参照IDを検証。可能なら別ブラウザ/別環境で復元試験（本番DBに対して無検証の復元はしない）。
3. 提供ZIPの大量の未コミット変更をコミット/退避してから変更する。`git reset --hard`、`git clean -fd`、IndexedDB初期化は禁止。

### 8.2 自動テスト例

- 更新対象の件数/IDを維持、異なる釣行IDへの移動拒否、終了済み釣行編集。
- カタログ/所有/手入力の切替、任意項目のクリア、魚種スナップショットの更新と削除。
- v1–v7 からのスキーマ互換、旧バックアップ復元、新魚種グループの検証。
- RC18の取り込み冪等性、ルアー/魚種の重複回避。
- （バラシ対応時）キャッチ数に含めないこと、既存の実釣データが `caught` と表示されること。
- `npm run build`、既存ユニットテスト、iPhone Safari/PWAで編集後の再起動・オフライン操作を確認。

## 10. Git作業手順

ローカルでの想定ブランチ: `feature/rc19-catch-edit-fish-lures`。

**注意**: 提供ZIPのHEADは `main` だが作業ツリーに多数の未コミット変更がある。後からGitHubの `main` だけをcloneしても同じコードにはならない。今回はユーザー提供ZIPを展開した作業コピーでブランチを作った。GitHubへのpushは未実施。

作業PC上で、現在の変更を確認した後、まだブランチを切っていなければ:

```powershell
git status --short
git switch -c feature/rc19-catch-edit-fish-lures
# まず引き継ぎ時点の変更を確認してコミットする（意図しない秘密情報やバックアップを含めない）
git add -A
git diff --cached --stat
git commit -m "chore: preserve pre-RC19 working baseline"
# 仕様書を docs/rc19/RC19_SPEC.md に追加してから
git add docs/rc19/RC19_SPEC.md
git commit -m "docs: define RC19 field-test requirements"
git push -u origin feature/rc19-catch-edit-fish-lures
```

※ローカルで既に同名ブランチが存在する場合は `git switch feature/rc19-catch-edit-fish-lures`。未コミットファイルの内容確認なしに `git add -A` を実行しないこと。
