# RC25 PR2 釣行別・時間別気象データ

2026-10-18実装。基準mainは `f81e29e`（PR #22マージ済み）。ブランチは `feature/rc25-pr2-hourly-weather`。

釣行詳細の「気象データ」から、手動設定したWGS84地点の過去の時間別気象を取得・保存・表示できる。気象はモデル・格子点に基づく推定値として扱い、施設での実測値とは表示しない。統合グラフはPR3で実装する。

## 操作方法

1. ホームの「最近の釣行」から対象釣行の詳細を開き、「気象データ」を展開する。
2. 緯度（-90〜90）・経度（-180〜180）を入力し、「地点を保存」を押す。施設名・施設IDは既存釣行からコピーする。地点保存だけでは通信しない。
3. オンラインで「過去の気象データを取得」を押す。再取得は同じ場所の「過去の気象データを再取得」。表示される期間・地点を確認する。
4. 保存後は圏外・アプリ完全再起動後も同じ一覧を閲覧できる。取得失敗・提供待ちの場合は、保存済みデータを残し、後日手動で再試行する。

表示項目は気温℃、直前1時間の降水量mm、10m風速m/s、相対湿度%、地表気圧hPa、WMO天気コード。海面更正気圧ではない。欠損はnullで保存して「—」と表示し、0や推測値へ補完しない。表は表の内部だけ横スクロールできる。

## 日付と取得方式

対象日は `startedAt` のAsia/Tokyo日付から `endedAt` の同日付まで。例の `2026-10-16T21:03:12.160Z` は10月17日06:03 JSTなので、保存済み `fishingDate: 2026-10-16` は変更せず、不一致を画面に案内する。終了日が翌日なら両日を取得する。開始日・終了日を含む日単位の全時間帯を保存する。釣行中で終了日時がない場合は開始日のみを対象とし、終了後の再取得で終了日まで含める。

APIのunixtime秒をUTC Unixミリ秒へ変換して `timestamp` に保存し、表示はAsia/Tokyo固定。取得・設定日時はUTCのISO文字列。釣果・イベントのDateとは `getTime()` で比較できる。

通信先は `https://archive-api.open-meteo.com/v1/archive` のみ。`timezone=Asia/Tokyo`、`timeformat=unixtime`、`wind_speed_unit=ms`、`temperature_unit=celsius`、`precipitation_unit=mm` を固定し、6項目のhourlyを指定する。モデル選択はAPI既定のBest Match。APIから基盤モデルの確定名が返らないため、ERA5等の特定モデルだったと断定して保存しない。

当日・未来日を含む期間は取得待ちにする。過去日でもAPIの未提供・全欠損は待機を案内する。予報APIへの切替、起動・釣行中の自動通信、自動再試行はない。1940年以降、1釣行の取得範囲は366日以内。20秒の通信タイムアウト、ユーザー中止、HTTP 400/429/5xx、不正な応答・単位・重複時刻を処理する。

## DB v8 / バックアップv7

DB v8は既存16テーブルの定義・ID・レコードを変更せず、次の3テーブルだけを追加する。移行コールバック、既存記録の補完、初期化はない。全19テーブルになる。

| テーブル | 主キー / インデックス | 内容 |
| --- | --- | --- |
| tripWeatherLocations | tripId | 手動入力座標、WGS84、locationSource=manual、施設ID・名称、updatedAt |
| tripWeatherHours | [tripId+timestamp] / tripId, timestamp, requestId | UTCミリ秒、6気象値、取得ID、fetchedAt。複合主キーで同一時刻の重複を防ぐ |
| tripWeatherRequests | ++id / tripId, createdAt | 対象期間・開始終了日時のコピー、使用地点、API名・endpoint・Best Match指定、応答グリッド座標・標高・タイムゾーン・オフセット、取得日時、状態、欠損数、出典・CC BY 4.0のURL・単位 |

手動地点とAPI応答のグリッド地点は別々に保存・表示する。地点を変更しても過去の保存データを消さず、次の取得成功まで前の地点・期間のデータであることを表示する。各時間行の `requestId` から、実際にその値を取得した地点・期間・出典を追跡できる。

再取得は、ネットワーク通信をトランザクション外で実施し、全応答検証後に気象時間行と成功メタデータを同一トランザクションで更新する。更新対象は当該釣行の気象だけ。取得失敗、全欠損、同一地点で欠損が増えた応答では前回の時間行を保持する。取得中に地点・釣行期間が変わった場合、釣行削除・復元で取得記録が消えた場合、別画面でより新しい取得が開始された場合も古い応答で上書きしない。中断したpending記録は再起動後に手動再試行を案内する。

気象テーブルに記録があればバックアップv7で全19テーブルを出力する。気象がない場合は既存のデータ依存形式を維持し、通常は施設を含むv6・16テーブルになる。v1〜v6の入力は引き続き読み込める。v7は全テーブル、参照、複合キー、時刻、単位、欠損・成功状態を検証してから書く。不正な復元はトランザクションごと中止する。

ユーザーが明示的にバックアップ復元を確定した場合、釣行・釣果等と同様に気象もバックアップの内容へ置き換える。v1〜v6には気象がないため、復元前の気象を同じIDの別釣行へ付け替えないよう引き継がない。確認文にこの挙動を追記した。施設・エリア・公式マスターは既存のマージ・衝突拒否を維持する。通常の起動・移行・気象取得で既存データを消去する処理はない。

ユーザーが確認して釣行を削除する既存操作では、当該釣行の気象も関連記録として削除する。確認画面に時間数・地点・取得履歴の対象を表示し、他釣行には触れない。開発用全削除も新テーブルの整合性を維持するよう追従したが、通常プロフィールや公開環境では実行していない。

## 座標候補・既存データの保護

PR #22の `approvalStatus: pending`、`distributionEnabled: false` を確認した。候補JSONの自動同梱・参照・正式採用は行わない。正式 `facility-master.v1.json`、配布ゲート、他マスター、既存snapshot、依存、workflow、PWA更新方針は変更していない。正式施設マスターのSHA-256は `30514d6674b413a70e9d830b4e5a4230bc83b13feb4e2f876daeadd67d33fb9c`。

`locationSource` と施設ID・名称を地点レコードに分けたため、将来の承認済み座標は、明示的な選択・出典検証を追加して扱える。現段階で許可しているsourceはmanualだけ。

## Open-Meteoの条件確認

2026-10-18に[公式利用条件](https://open-meteo.com/en/terms)、[ライセンス](https://open-meteo.com/en/licence)、[Historical API仕様](https://open-meteo.com/en/docs/historical-weather-api)を確認した。無料APIは非商用限定で、600回/分・5,000回/時・10,000回/日未満等の制限がある。ユーザーは事前方針を了承済み。本実装は個人・非商用向けでAPIキーを同梱せず、商用化時には有料契約・キーを安全に扱う構成の再検討が必要。

データはCC BY 4.0。表示箇所の出典リンク、ライセンスリンク、時刻整形・欠損表示の加工説明を `WeatherAttribution.vue` に共通化した。PR3のグラフもこのコンポーネントを再利用する。出典・帰属・ライセンスURL・単位は取得メタデータにも保存してバックアップへ含める。Open-Meteoサーバーのソース実装は取り込んでいない。

公式仕様上、データセットごとに更新間隔・提供遅延が異なり、ERA5系には数日の遅延がある。特定日に必ず取得できるとは扱わない。通信は利用地点と日付を外部サービスへ送るため、取得操作の付近に説明を表示した。Service WorkerにAPI応答をキャッシュする設定は追加せず、圏外閲覧はIndexedDBから行う。

## 実データフィクスチャ

2026-10-17・日本イワナセンター相当の手動テスト地点 `36.611, 139.194` について、実Historical API応答を2026-10-18に取得した。24時間分を未改変のJSONとして保存し、URL・取得日時・SHA-256・帰属・ライセンスをprovenance JSONに記録した。応答のグリッド地点は `36.590508, 139.12303`、標高736m。入力地点とは異なるため、両方が保存されることを試験している。テスト地点を正式施設座標として採用・配布していない。

E2Eは保存済み応答のモック再生のみを使い、実行中に外部APIへ依存しない。06:03〜15:25 JST、元fishingDateは10月16日、7匹の釣果時刻は06:21・10:13・11:22・13:57・14:21・14:53・15:16として隔離テスト用データを作成した。ペレット散布の正確な時刻は不明なので、その釣行にイベントを追加していない。欠損・エラー試験はフィクスチャの派生モックで、実際の気象値として扱わない。本番記録・iPhoneのIndexedDB・本番バックアップは使っていない。

## iPhone実機でのレビュー手順

1. 本番とは別のテスト用URL・端末プロフィールを使う。必要なら実機確認前に現在のデータをバックアップする。本番データを復元試験に使わない。
2. テスト用釣行の詳細で「気象データ」を展開し、緯度・経度・地点保存・取得ボタンへスクロールして操作できることを確認する。
3. 取得後、入力地点とモデルのグリッド地点、JST日付、単位・欠損表示・出典リンクを確認する。
4. 機内モードで完全終了・再起動し、保存済み表を閲覧できること、再取得を押して失敗しても表が残ることを確認する。
5. テスト環境でv7バックアップを書き出し、別の隔離環境で復元して地点・24時間分・取得メタデータが一致することを確認する。

## 未解決事項とPR3

iPhone Safari実機は未確認。ChromiumのiPhoneサイズ・タッチ条件とオフライン完全再起動は自動試験した。APIの可用性・将来の仕様/規約変更、モデル誤差、手動座標の入力間違いは残る。Best Matchの基盤モデルは時期・地点で変わり得る。保存地点・グリッド地点・取得日時を確認して使う必要がある。

PR3では、`tripId` とUTCミリ秒で気象・釣果・バラシ・既存 `tripEvents` を結合し、時間帯・欠損・取得地点差を示すグラフを追加する。既存イベントの `occurredAt` はDateとして十分なので、このPRでイベントテーブルを増やしていない。時刻不明のペレット散布は、精度・時間範囲や不明状態をどう入力・表示するかを決め、正確な時刻へ補完しない。グラフでも共通帰属表示を使い、地表気圧と直前1時間降水量の意味を維持する。
